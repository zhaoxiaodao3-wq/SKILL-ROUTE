# 04 · 资产盘点与分类

> **只读盘点**，没有移动、修改、删除任何现有文件。分类结果用于 [05-改造映射.md](./05-改造映射.md)。
> 数据来源：`glob` / `grep` / 直接读文件，时间 2026-11-17。

---

## 0. 一句话结论

这个仓里其实有 **8 类资产、约 2.1 万个文件**，但只有 **2 个文件**是每个项目都需要的运行时。
其余是技能（44 份副本）、文档体系（7 个版本）、编辑器（2 万文件）、安装器和规则文案——它们被混在一起分发，所以"乱"。

---

## 1. 先纠正一个认知：这是源仓，不是应用

| 检查项 | 结果 | 含义 |
|---|---|---|
| `package.json` | ❌ 不存在 | `pnpm harness:*` 在本仓跑不了 |
| `scripts/` | ❌ 不存在 | 校验器不在本仓 |
| `src/` | ❌ 不存在 | 本仓没有业务代码 |
| `.agents/`、`docs/superpowers/` | ✅ 存在 | 技能 + 流程文档 |

所以：**本仓 = 技能与流程源仓**，真正的可执行部分（`scripts/harness/`、`pnpm` 脚本）装在消费方项目里（如 `e:\code\frontend`，通过 junction 指回本仓）。
这一点决定了改造方向：**源仓管"内容"，消费方只管"生成物"**，两边不能混。

## 3. 分类明细

### A 运行时（2 文件）

| 文件 | 作用 | 问题 |
|---|---|---|
| `SKILL_ROUTING.md` | 机器块 JSON（14 条记录）+ 人类可读说明 | 同时当"全集"和"本项目路由表"用；含脏数据（见第 5 节） |
| `router.mjs` | `--annotate` / `--list` / `--validate` / 自由文本 | 不校验 skill 是否存在；Windows 下 `isMain` 判等会静默退出 |

**处置：** 保留，但拆成"仓库全集 `graph.json`"和"项目子集 `SKILL_ROUTING.md`"两份。

### B 编排技能（3 个）

`superpowers-harness-run`（端到端入口）、`superpowers-harness`（安装 + 门禁）、`superpowers-demand-workflow`（目录规范）。

**问题：** 三者互相引用，但 bootstrap 只装前两个，第三个只装了 scripts/docs，不装技能本体。

**处置：** 保留，改为"整包同步"，依赖闭包一起装。

### C 能力技能（25 个）

`.agents/skills/` 共 28 个技能，除 B 的 3 个外有 25 个，例如 `figma-long-page`、`echarts`、`tailwind-design-system`、`ccar-pdf-static-html`、`thymeleaf`、`openspec-*`、`source-command-*`、`git-submitter` 等。

**问题：** 28 个里只有 13 个进了路由图，**覆盖率 46%**。剩下 15 个技能人工知道要用，但机制上选不到。

**处置：** 保留，但按项目用 `capabilities.json` 挑子集；未入图的要补或不装。

### D 编辑器（约 2 万文件）

`electron/main.mjs`、`panel/`（Vue+Vite）、`server.mjs`（6 个本地文件 API）、`release/win-unpacked/`、`_baota-upload/`、两套 `node_modules/`。

**问题：** 与运行时同目录、同分发、同版本，导致新项目接入 = 接入一个 Electron 工程。

**处置：** 整体移出到源仓 `tools/`；线上改为"静态站 + 提交 PR"，`server.mjs` 下线。

### E 文档体系

`docs/superpowers/`：`current-version.txt` = **V1.7.1**；版本目录 7 个（`v1.0`、`v1.4.8`、`v1.4.9`、`V1.5.0`、`V1.6.0`、`V1.7.0`、`V1.7.1`）；根文件 `HARNESS_RULES.md`、`SUPERPOWERS_RULES.md`、`GUIDE.md`。

**问题：** 规则文件与历史模块混在一棵树里，每次 bootstrap 都要判断"哪些是模板、哪些是历史"。

**处置：** 拆成"模板（`references/`，随技能走）"与"项目实例（`docs/superpowers/`，随项目生成）"。

### F 安装器

`superpowers-harness/scripts/bootstrap-harness.ps1|.sh`、`validate-harness.mjs`、`status.mjs`、`validators/`（含 4 个测试文件）。

**问题：** 硬编码路径（第 143–146 行）；"一边强覆盖、一边跳过"两套策略；装完不校验。

**处置：** 保留，重写 sync 段：lock + 缓存 + 生成 + 校验，失败即失败。

### G 代理入口

| 文件 | 内容 | 问题 |
|---|---|---|
| `.cursorrules` | 22 行，8 条流程规则 | 只对 Cursor 生效；DSH 无等价物 |
| `.cursor/commands/harness.md` | 25 行，`/harness` 命令 | 入口只有"人喊"这一条路 |

**处置：** 保留 `.cursorrules`，新增 `AGENTS.md` 作为跨代理常驻指令；`/harness` 降级为兜底。

### H 冗余与垃圾

| 项 | 证据 | 处置 |
|---|---|---|
| 路由图里的测试条目 | `id: "阿斯顿"`、`name: "阿1斯顿"`、`path: "D:\\360Downloads"`、`triggers: []` | 删除 |
| 三套陈旧副本 | `.agent/skills`（4 个）、`.claude/skills`（4 个）、`.cursor/skills`（8 个）都只有 openspec 系 | 归一到 `.agents`，其余生成 |
| 构建产物 | `release/win-unpacked`、`_baota-upload/`、`graph.cache.json` | 移出分发路径 / 加 ignore |
| 机器相关配置 | `local-config.json`（含本机绝对路径） | 不进仓库版本控制 |

## 5. 路由图体检（14 条记录）

| 检查项 | 结果 |
|---|---|
| 真实条目 | 13 |
| 垃圾条目 | 1（"阿斯顿"，path 指向 `D:\360Downloads`） |
| 相对路径（可移植） | 7 条：`../skills/...` |
| **绝对路径（换机必坏）** | 6 条：`E:\code\frontend-local\.agents\skills\{frontend-design, tailwind-design-system, improve-animations, tailwindcss-animations, echarts, accessibility}` |
| 图内技能 vs `.agents/skills` 实际 | 13 / 28 → **覆盖率 46%** |
| 是否校验 path 存在 | ❌ `router.mjs` 从不检查 |

**结论：这份图本身已经是"脏"的，不能作为跨项目复制的源。** 这也解释了为什么新项目复制过去必然错配——13 条里 6 条写死了盘符，1 条指向下载目录。

## 6. 归类结论（一句话决策表）

| 类 | 归属 | 动作 |
|---|---|---|
| A 运行时 | 项目内 `.agents/routing/` | 生成（不手搬） |
| B 编排技能 | skills 仓库 | 移动 + 整包同步 |
| C 能力技能 | skills 仓库 | 移动 + 按 `capabilities` 挑选 |
| D 编辑器 | 源仓 `tools/` | 移出 + Electron 下线 |
| E 文档体系 | 模板进仓库 / 实例进项目 | 拆分 |
| F 安装器 | skills 仓库 | 保留 + 重写 sync |
| G 代理入口 | 项目根 | 保留 + 新增 `AGENTS.md` |
| H 冗余垃圾 | — | 删除 / 移出 / ignore |

下一步：这些东西具体怎么挪、挪到哪、什么顺序，见 [05-改造映射.md](./05-改造映射.md)。
